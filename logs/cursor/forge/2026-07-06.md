## [Cursor Log] Manual pick "start from the top" drag broken — DEMAND

**Symptom:** Choosing your own route sequence, dragging a picked stop to the top of the order window did nothing — Apply routed the old order.

**Root cause:** `RoutePickOrderDialog` committed order changes only via `model().rowsMoved`. `QListWidget` `InternalMove` implements a drop as insert-copy + remove-source, so `rowsMoved` never fires. Drag reorders (incl. move-to-top) updated the visible list but never emitted `order_changed`, so the parent kept the stale `_route_pick_uids` and `apply_manual_order` traced the pre-drag sequence. Up/Down/Remove buttons worked (they emit directly), which is why it was intermittent.

**Fix:**
- `ui/route_pick_dialog.py` — `_ReorderList(QListWidget)` overrides `dropEvent` to emit a deferred `dropped` signal after every real drop; dialog commits the settled order via `_on_list_dropped` → `_emit_order_from_list`. Kept the `rowsMoved` connection for platforms that do emit it.
- `scripts/test_route_pick_clicks.py` — new `test_drag_reorder_commit`: reproduces the stale-order precondition (take/insert without `rowsMoved`), fires the drop commit, asserts the parent order updates and `apply_manual_order` starts at the chosen top stop.

**Hardening (belt-and-suspenders):** headless tests can't drive Qt's native drag loop, so drop-signal delivery can't be fully auto-proven. Added `RoutePickOrderDialog.current_order()` + `_sync_pick_order_from_dialog()` so `_route_pick_apply` re-reads the list order at Apply time — the routed sequence always matches what the operator sees even if a drop-commit signal is ever missed. Regression test simulates a totally missed signal.

**Proof:** `scripts/test_route_pick_clicks.py` PASS (drag-to-top commit + missed-signal Apply adoption); `scripts/smoke_full.py` exit 0. Push held (branch `main`).
